# Hydrogen v2.3.0-preview.3

Channel: **preview**. The owner approved publication of the explained response-retention fix. Deployment is separately owned by runtime task `01a0fd0f-29a3-72ef-80bc-42140e9b4029`; this release task does not access or mutate production.

## Behavior

- Response expiry runs in one dedicated worker after listen instead of synchronously at startup, every minute and during settings save. Existing age indexes feed bounded candidate pages and primary-key deletes; conversation protection no longer uses a correlated status scan.
- Cleanup uses completion-relative scheduling, keeps committed progress after contention, rechecks retention policy between batches and never overlaps workers or falls back to inline expiry.
- Restore confirms worker exit before changing the database. Shutdown cancels maintenance. Foreground write transactions reserve before guard reads, and backup export reads one consistent snapshot for concurrent maintenance.
- Terminal/running status rules, age boundaries, zero/default/invalid retention semantics and foreign-key cascades are preserved. Configuration, image cache, manual deletion, session snapshots and existing ownership boundaries retain their semantics.

The v2.2.3 startup-statistics and request-log fixes did not cover this response-expiry path. Production's approved retention-0 bypass supports the cleanup hypothesis but does not prove the exact previously active SQL. A 32-candidate batch, 64-batch cycle and 1-second between-call budget do not hard-bound individual native calls, active-set scans or cascades under severe I/O pressure.
