# Hydrogen v2.1.5

补丁版本，修 v2.1.4 引入的**服务端工具往返**在两种客户端协议上的保真度问题。这些问题的发现方式是：把我们的输出逐字段对照 Anthropic 服务端工具文档、Anthropic 官方 SDK 与 OpenAI 官方 SDK 的类型定义。

## 修复

- **多轮往返不再丢中间内容。** 此前把往返块**前插**到最终响应前面，结果是：第一轮说"让我搜一下"、随后调用工具，客户端只收到「调用 + 结果 + 最后一轮答案」——第一轮的文字被静默丢弃，且块的位置也不对。现在 content 从本次运行的完整历史重建，按协议定义的顺序保留每一轮：**文字 → 调用 → 结果 → 最终答案**，全部在同一条 assistant 轮内。

- **Anthropic 结果块补齐规范字段。** 结果块现在带必需的 `caller: { "type": "direct" }`；服务端调用的 id 也改用 `srvtoolu_` 前缀，与客户端工具调用区分。

- **失败改用协议自己的错误对象。** 此前失败是「空数组 + `is_error: true`」，现在按规范发出 `content: { "type": "web_search_tool_result_error", "error_code": … }`。错误因此**不可能**被读成"搜索无结果"——这是两种不同的事实。

- **Responses 侧改成该协议的原生形态。** 这个协议**没有独立的结果块**：一次服务端调用就是**单个 `web_search_call` item**，来源 URL 放在 `action.sources`（该协议只收 url）。此前按 Anthropic 的形状发，不规范。现在缓冲与流式两条路径都是规范形态。

- **Responses 的服务端工具声明能被识别。** `{ "type": "web_search" }`（以及版本化拼写）现在与 Anthropic 的 `web_search_20250305` 一样参与契约匹配。

- **实时流不再绕过往返合成。** 声明了服务端工具的请求不再走实时透传路径——那条路会把模型这一轮直接流出去，正好跳过需要合成往返的那一轮。这类请求改走缓冲路径并伪造流，客户端两种模式下收到的块一致。

## 错误码由适配器决定（新增契约）

失败的原因码**由适配器给**，通过它已经掌握的那个 `resultPath` 表达：

```json
{ "results": { "type": "web_search_tool_result_error", "error_code": "max_uses_exceeded" } }
```

可用码是客户端协议的闭集：`invalid_tool_input`、`unavailable`、`max_uses_exceeded`、`too_many_requests`、`query_too_long`、`request_too_large`。

**只有适配器没有声明可用原因时，Hydrogen 才填 `unavailable`** —— 包括指针选不到数组、返回非数组、JSON 无法解析、调用超出预算。日志里记录真实原因，便于区分配置错误与上游故障。自造的原因码不会被写到线上。

## 已知限制（写入文档）

- **`encrypted_content` 无法产生。** 它是 Anthropic 生成的不透明令牌，供模型复用上次检索而无需重搜；代理自己执行搜索时造不出该值。不读该字段的客户端不受影响。
- **`citations` 不发送。** 它要求"模型实际引用的原文与字符区间"，适配器提供不了，因此不伪造——客户端会拿到标题与链接、没有摘要片段。
- **服务端循环不会 `pause_turn`。** Hydrogen 在内部跑完整个循环；到达轮次上限时按失败处理，客户端没有"原样重发以续跑"的手段。

## 升级与兼容性

- 无数据库变更：`serverTool` 仍是工具定义中新增的可选字段，旧工具不受影响。
- 未配置契约的工具、未声明服务端工具的客户端**行为不变**。
- 已按 v2.1.4 方式配置了契约的用户无需改动配置；但若适配器此前靠"返回非数组"表达失败，现在建议改为显式返回错误对象以给出准确原因码（不返回也仍然安全，只是原因记为 `unavailable`）。
- 若客户端此前解析 v2.1.4 的 `is_error: true`，现在应读取协议的错误对象 / `status: "failed"`——这正是本次修复的目的。
