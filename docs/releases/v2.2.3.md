# Hydrogen v2.2.3

Local release candidate; publication and container CI are pending coordinated release. No remote branch push, tag, GitHub Release, image publication or production deployment has been performed by this task.

This patch reduces startup statistics read amplification and isolates that aggregation from the HTTP event loop. It also avoids an unnecessary request-log table traversal when retention is already within its row budget.

## Startup statistics and diagnostics

- Replaces five seed/catch-up SQL aggregates with one ordered scalar iterator over a fixed request-ID interval. It does not select or deserialize log bodies or JSON payloads.
- Starts a single readonly statistics worker after the HTTP listener opens. A fully caught-up cache skips the worker and aggregation entirely.
- Returns HTTP 503 with `Retry-After: 5` and an explicit initialization/unavailable code from all administrator statistics endpoints until totals are ready, including date-range queries. Health, login and the rest of the application can run while this worker initializes. The existing Overview error display asks for reload.
- Captures the historical upper ID before serving, then merges live requests above that boundary once. Retains all-time history and the existing cache format; incomplete totals are not persisted. Clear/restore invalidates obsolete worker results.
- Defers request-log pruning until statistics are ready, preserving rows needed for catch-up. Worker failure leaves the prior complete cache and request logs intact.
- Adds static startup stage, phase and timing markers around database setup, migrations, key/admin initialization, Responses recovery/cleanup, statistics and listener startup. New diagnostics contain no SQL, parameters, file paths, credentials or payloads.
- Bundles `stats-worker.cjs` alongside the production server; the existing Docker artifact copy includes both. Development mode and explicit migration/web paths outside the repository working directory are supported.

## Request-log row cap

- Checks the exact row count through a small covering index before the existing retention threshold query. When the table is within its budget, pruning returns without the previous OFFSET table traversal.
- Above-budget pruning retains the same newest-by-ID boundary and deletion behavior.

## Compatibility and limits

- No database migrations, new indexes, dependency changes or credential/permission changes are required. Root/workspace versions and lockfile version metadata are synchronized at 2.2.3.
- Required SQLite setup, schema migrations, master-key verification and Responses recovery/retention still execute before listen. Ordinary request database operations, ready date-range queries and pruning remain synchronous.
- Scalar reads may still require physical overflow pages. A long readonly snapshot can retain WAL while requests write; failed initialization postpones log pruning. Group-result transfer, cache merge/serialization and persistence still consume main-thread resources.
- This fixes demonstrated local startup-statistics paths. The production incident's active SQL and storage cause were not captured, and the production service recovered after its separately authorized restart without this patch. No corruption, hardware-failure diagnosis or production-scale cure is claimed.
- Runtime requirements remain Node 22.12+; the container uses Node 22. Existing published tags are preserved. Release publication does not imply a production upgrade.

## 中文摘要

- 无迁移及依赖升级；线上具体阻塞 SQL 仍未证实，本轮不部署服务器。
